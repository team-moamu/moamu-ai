# 6개 도전 이미지 데이터셋 및 프롬프트 정량평가 계획

| 항목 | 내용 |
|---|---|
| 상태 | 2026-11-02 소규모 파일럿 실행 완료; 정식 성능 검증은 미완료 |
| 작성일 | 2026-11-02 |
| 범위 | 공부, 계단 운동, 물 마시기, 알고리즘 학습, 영양제, 명찰 사진 판정 |
| 기준 모델 | Gemini API / `gemini-3.5-flash-lite` |
| 기준 프롬프트 | `photo-verification-v2` |

## 1. 목적

현재 Gemini 결과에는 초기 긍정 스모크 테스트와 2026-11-02 개발 파일럿이 포함되어 있다. 둘 다 소규모 진단용이며, 이 계획의 목적은 다음과 같다.

1. Open Images 외 데이터에서 여섯 도전의 조건을 시험할 사진을 확보한다.
2. 각 사진에 조건별 정답 라벨을 붙여 현재 프롬프트의 오승인·오거절·판정 보류를 측정한다.
3. 결과를 보고 현재 지침을 유지할지, 어떤 문장을 바꿔야 할지 결정한다.
4. 모델 버전, 프롬프트 버전, 데이터셋, 비용과 결과를 재현할 수 있게 기록한다.

공개 데이터셋의 클래스 라벨만으로 MOAMU 조건을 모두 판정할 수는 없다. 일반 객체나 행동 라벨은 후보 사진을 찾고 일부 라벨을 보강하는 데 쓰고, 실제 인증 조건은 사람이 이미지별로 확인한다.

## 2. 현재 기준선과 한계

- Open Images V7: 이미지 1장, 객체 조건 2개를 Gemini로 확인했다. 두 조건 모두 기대값과 일치한 연결 스모크 테스트다.
- Pexels: 여섯 도전 유형에 긍정 사진 3장씩, 총 18장을 사용했다. 최초 문구에서 36개 조건 중 35개가 `MET`, 1개가 `NOT_MET`이었다. 영양제 조건 문구를 고친 뒤 관련 3장을 재평가해 6개 조건이 모두 `MET`였다.
- 이 18장은 모두 긍정 사례이며 사람이 한 차례 검토한 라벨이다. 음성·모호 사례가 없어 오승인율을 계산하거나 일반 성능을 주장할 수 없다.
- 이전 긍정 스모크 실험은 `photo-verification-v1` 기준이다. 조건 ID와 설명만 모델에 보내는 `photo-verification-v2`를 2026-11-02 파일럿에서 새 기준선으로 측정했다.
- 과거 매니페스트에는 백엔드 확정 전의 `OBJECT_VISIBLE` / `ACTION_VISIBLE` 값이 남아 있다. 새 API 평가는 백엔드가 확정한 여섯 템플릿의 조건 스냅샷과 실제 `condition_type`을 사용한다.
- 2026-11-02에 v2를 Pexels 사진 30장(기존 긍정 18장 + 새 혼합 조건 사례 12장)으로 실행했다. 조건 예측 60개 중 57개가 기존 라벨과 일치했고, `NOT_MET` 라벨 12개 중 1개를 `MET`으로 오승인했다.
- 해당 오승인(비타민 구미 사진을 정제·캡슐 조건으로 오인)을 v3의 집중 재평가에서 해결하지 못했다. 형태를 명시한 지침을 추가한 v4를 같은 30장으로 재평가한 결과 58/60 예측이 일치했고 오승인은 0/12였다. 기존 공부 긍정 사례 한 조건이 `UNCERTAIN`에서 `NOT_MET`으로 바뀌어 오거절 1건이 생겼다.
- 이 30장 파일럿은 프롬프트 오류를 찾는 진단용이다. 도전별 부정 조건 표본은 각각 2개뿐이므로 PRD의 오승인율 5% 목표 달성을 입증하지 않는다. 실제 백엔드 조건 스냅샷과 두 명의 독립 라벨 검수가 아직 필요하다.

전체 결과와 신규 이미지 출처·해시는 [2026-11-02 파일럿 결과](six-category-v2-pilot-20261102.md)를 참고한다.

상세 기록: [벤치마크 로그](benchmark-log.md), [기존 6개 유형 스모크 테스트](six-challenge-positive-smoke.md), [프롬프트 실험 기록](prompt-experiments.md).

## 4. 데이터 수집과 라벨 기준

### 4.1 조건 스냅샷 고정

평가를 시작하기 전에 백엔드와 여섯 템플릿의 최종 인증 조건을 고정한다. 템플릿별로 `challenge_condition_id`, `code`, `condition_type`, `description`, `required`, `sort_order`를 보존하고, 실제 활성 도전 ID와 템플릿 시드 ID를 혼동하지 않는다. 조건 설명이 바뀌면 기존 평가 결과와 섞지 말고 데이터셋 또는 실험 버전을 올린다.

### 4.2 정답 라벨

각 이미지와 각 조건을 독립적으로 다음 중 하나로 라벨링한다.

- `MET`: 조건에 적힌 시각 증거가 이미지에서 명확히 보인다.
- `NOT_MET`: 이미지가 충분히 선명하고 맥락도 확인되며, 조건이 요구한 증거가 없거나 명시된 행동이 일어나지 않는 것이 분명하다.
- `UNCERTAIN`: 흐림·가림·작은 크기·모호한 장면 때문에 이미지 한 장만으로 확인할 수 없다.

행동이 사진 밖에서 일어났을 가능성만으로 `MET`를 주지 않는다. 데이터셋 주석에서 클래스가 빠졌다는 이유만으로 `NOT_MET`를 주지 않는다.

### 4.3 검수와 출처 기록

- 두 명의 검수자가 모델 결과를 보지 않고 독립적으로 조건별 라벨을 붙인다. 의견이 다른 항목은 근거를 기록하고 제3자 또는 공동 검수로 확정한다.
- 3개 라벨에 대한 검수자 간 일치도(Cohen's kappa)를 함께 기록한다. 일치도가 낮으면 모델 평가를 진행하기 전에 라벨 기준을 다시 맞춘다.
- 이미지 ID, 원본 URL, 출처 데이터셋/버전/분할, 사진별 라이선스, 수집 날짜, 로컬 파일 SHA-256을 기록한다.
- 같은 원본 이미지가 여러 데이터셋에 포함될 수 있으므로 원본 ID·URL과 perceptual hash로 중복을 찾아 같은 분할에 묶는다.
- 사진 원본은 저장소에 커밋하지 않는다. 매니페스트와 라벨만 저장하고 실제 파일은 `AI_IMAGE_ROOT` 아래에 둔다.
- Pexels와 연구 데이터셋은 각각 다른 이용 조건을 가진다. API에 이미지를 보낼 수 있는지와 팀 저장소에 원본을 둘 수 있는지를 별도로 확인한다.

매니페스트는 기존 JSONL 형식을 확장해 `case_id`, 데이터 출처, `image_path`, 조건 스냅샷, 조건별 `expected_results`, 라벨 근거를 포함한다. 사례별로 조건이 다를 수 있으므로 무작위 ID를 실제 백엔드 데이터인 것처럼 문서화하지 않는다.

## 5. 표본 규모와 분할

### 1단계: 프롬프트 진단용 파일럿

도전별로 명확한 성공 사진 10장, 명확한 실패 사진 10장, 판정이 어려운 사진 10장을 우선 목표로 한다. 총 180개 사진 사례다. 각 사진에 포함된 모든 조건을 라벨링하되, 조건별 세 클래스 표본 수를 별도로 집계한다. 조건마다 특정 클래스가 부족하면 그 결과로 해당 조건의 성능을 단정하지 않는다.

이 단계의 목적은 지침의 대표 오류를 찾고 평가 파이프라인을 점검하는 것이다. 10개 실패 사례로는 PRD의 오승인율 5% 목표 달성을 입증할 수 없다.

### 2단계: 품질 목표 확인용 확장

PRD에는 부적합 사진 오승인율 5% 이하, 적합 사진 승인율 85% 이상, 조각 반영 지연 p95 5초 이내가 제안되어 있다. 카테고리별로 오승인율 5% 이하를 뒷받침하려면, 독립적인 실패 사진 약 60장 이상에서 오승인이 0건이어야 95% 단측 상한이 대략 5% 아래로 내려간다. 오승인이 한 건 이상이면 더 많은 표본이 필요하다. 이 표본 수는 조건별 기준이 아니라 **도전별 전체 사진 판정** 기준이며, 조건별 안전성을 주장하려면 각 조건의 실패 표본을 별도로 늘린다.

적합 사진 승인율도 도전별로 보고 95% 신뢰구간을 함께 제시한다. 파일럿에서 통과한 카테고리만 골라 결과를 발표하지 않고 여섯 유형 모두의 표본 수와 성능을 공개한다.

### 분할 규칙

- 프롬프트를 조정하는 `dev`와 최종 확인용 `held_out`을 이미지 수집 시점에 나눈다.
- 같은 이미지·중복 이미지·같은 촬영 연속 컷은 모두 동일한 분할에 둔다.
- `held_out` 결과를 확인한 뒤 지침을 바꾸면 해당 세트는 더 이상 최종 시험 세트로 쓰지 않는다. 새 이미지로 다시 만든다.
- 여섯 유형, 조건별, 라벨별 표본 수를 매 실행 로그에 기록한다.

## 6. 측정 지표와 합격 판단

### 조건 단위

- 3-way confusion matrix, 조건별 및 macro-F1, class별 precision/recall.
- 오거절율: 정답 `MET` 중 예측 `NOT_MET` 비율.
- 판정 보류율: 예측 `UNCERTAIN` 비율.
- coverage: 전체 중 `UNCERTAIN`이 아닌 예측 비율.
- selective accuracy: `UNCERTAIN`을 제외한 예측의 정확도.

### 사진 제출 단위

PRD의 오승인·적합 사진 승인 목표는 사진 제출 단위로 계산한다. AI API는 조건별 상태만 반환하므로, 이 측정 전에 백엔드의 필수 조건 집계 규칙을 확정하고 그대로 재현해야 한다. 집계 규칙이 정해지기 전에는 조건별 지표만 공식 결과로 기록한다.

- 오승인율: 정답상 부적합한 제출 중 최종적으로 통과 처리된 비율.
- 적합 사진 승인율: 정답상 모든 필수 조건을 충족한 제출 중 통과 처리된 비율.
- 모호 사례의 `UNCERTAIN` 비율과 백엔드 검토 전환 비율.
- AI API 응답시간 p50/p95와 백엔드 전체 처리시간을 구분한다. PRD의 “조각 반영 지연” p95는 AI API 시간만으로 대체하지 않는다.

모든 비율에 95% 신뢰구간과 분모를 표시한다. 불균형한 클래스는 정확도 하나로 합치지 말고 macro-F1, 오승인율, 승인율을 함께 본다.

### 프롬프트 유지 또는 조정

1. 완료된 v2 기준선과 v3 보충 확인을 바탕으로 v4를 같은 `dev` 30장에 재평가했다. v4는 다음 검증 후보이며 품질 목표를 통과한 것으로 보지 않는다.
2. 추가 튜닝 전에 `STUDY_REVIEW/7516544` 라벨을 독립 검수하고, 카테고리별 부정 사례와 모호 사례를 보강한다.
3. 실패 사례마다 원인을 `조건 문구 모호`, `이미지 품질/가림`, `객체 혼동`, `행동 관계 오판`, `모델 출력 오류`, `라벨 불일치`로 분류한다.
4. 조건 설명이 모호하거나 사진 한 장으로 확인할 수 없는 문제는 프롬프트로 덮지 말고 백엔드 조건 정의를 수정하거나 `UNCERTAIN`/검토 정책으로 넘긴다.
5. 프롬프트 원인이 뚜렷하면 한 번에 지침 한 가지를 바꾼 새 버전을 만든다. 모델, 데이터 분할, 온도와 출력 스키마는 고정한다.
6. 같은 `dev` 사례에서 버전별 상태 변화율, 오승인율 변화, 승인율 변화, `UNCERTAIN` 변화를 비교한다.
7. 채택할 지침을 고정한 뒤에만 `held_out`을 한 번 실행한다.

PRD 기준을 만족하고 여섯 카테고리 중 특정 유형에서 큰 안전 오류가 없으면 현재 지침을 유지한다. 오승인율이 5%를 넘거나 적합 사진 승인율이 85%보다 낮으면 오류 원인을 먼저 분리하고, 프롬프트 문제일 때만 튜닝한다. 지표가 목표를 만족하더라도 표본 수와 신뢰구간이 충분하지 않으면 “통과 입증” 대신 “파일럿 통과”라고 기록한다.

## 7. 호출 예산과 실행 순서

Gemini 벤치마크 실행기는 한 번 실행에 최대 6개 이미지 사례만 허용한다. 이 제한은 누적 비용을 자동으로 막지 않는다.

1. 매니페스트 검사와 `--execute` 없는 dry-run으로 경로·라벨·분할을 확인한다.
2. 첫 라이브 배치는 최대 6장으로 실행하고 결과 JSON, 토큰량, 소요 시간, 실제 청구 내역을 확인한다.
3. 기존 예산 요청에 맞춰 전체 호출의 상한을 30,000원으로 두고, 누적 추정액과 실제 청구액을 별도 기록한다. 상한 도달 또는 예상 밖의 호출량이면 다음 실행을 중단한다.
4. 필요할 때 6장 단위로 추가 실행한다. 동일 파일럿을 재실행해도 별도 호출·비용으로 집계한다.

실행 예시:

아래 `six-category-pilot-01.jsonl`은 파일럿을 만들 때 사용할 매니페스트 경로 예시다.

```bash
# 데이터/경로 검증만 수행
moamu-evaluate --manifest data/evaluation/six-category-pilot-01.jsonl --provider gemini --limit 6 --prompt-version photo-verification-v2

# 명시적으로 최대 6장까지 Gemini 호출
moamu-evaluate --manifest data/evaluation/six-category-pilot-01.jsonl --provider gemini --limit 6 --prompt-version photo-verification-v2 --execute
```

실제 호출 전에는 `GEMINI_TOKEN_API_KEY`와 모델 설정을 확인한다. 결과 파일은 기존 규칙대로 `data/evaluation/results/`에 두고 Git에 올리지 않는다.

## 8. 산출물

- 데이터셋 인벤토리: 출처·라이선스·원본 이미지 ID·SHA-256·분할.
- JSONL 매니페스트: 실제 API 조건 스냅샷과 조건별 사람 라벨.
- 라벨 검수표: 검수자별 결과, 불일치, 최종 조정 근거.
- 실험 기록: 모델 ID, SDK, prompt version/hash, 데이터 revision, 이미지 호출 수, 토큰, 비용, p50/p95.
- 결과 표: 여섯 유형별 confusion matrix, macro-F1, 오승인율·승인율, `UNCERTAIN`, 95% 신뢰구간.
- 오류 사례 요약: 원본 사진 자체는 저장소에 넣지 않고 사례 ID와 오류 유형만 기록.
